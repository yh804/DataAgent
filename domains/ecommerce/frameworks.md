# 电商领域包 · 决策骨架

> 版本:v0.2 · 状态:草案(业务口径未确认)
> 用途:把 spec.md 的 3 个决策问题翻译成可执行的指标分解、漏斗与澄清清单。
> 不新增任何 Python 依赖,所有指标 id 都来自 metrics.yaml。

## 1. 北极星指标候选(status: draft)

业务需要一个能贯穿不同渠道、品类与时间窗的「北极星指标」来对齐团队。本包**不替业务拍板**,
三个候选并列,默认报告里三个都列,并在结论里注明本次分析采用了哪个口径。

### 候选 A:净 GMV

- **定义公式**:`净 GMV = SUM(orders.支付金额) − SUM(orders.退款金额)`,
  筛选条件与 `gmv` 指标一致,额外扣除 `退款中` 与 `已退款` 订单的 `退款金额`。
- **能回答什么决策**:真实收入规模是否达标、活动带来的收入净增长、退款成本侵蚀程度。
- **被操纵的风险**:
  - 宽松退款政策会抬高退款金额,净 GMV 被压低;
  - 财务口径与运营口径不一致时会出现两套数字;
  - 跨期退款只按原订单日期归属,没有退款时间列。
- **当前数据能否算**:**能**。`orders` 表同时有 `支付金额` 与 `退款金额`,
  只需在 `gmv` 的干净口径上做减法。属于 metrics.yaml 候选块,尚未作为独立指标登记。

### 候选 B:支付用户数(去重)

- **定义公式**:`COUNT(DISTINCT orders.用户ID)`,筛选条件与 `order_count` 一致,
  排除测试单、刷单、内部账号、测试账号、待支付 / 已取消订单。
- **能回答什么决策**:用户规模增长是靠新客还是复购、各渠道的覆盖人群有没有重叠、
  客单价下降是否因为拉进了一批低价值用户。
- **被操纵的风险**:
  - 内部账号 / 测试账号混入;
  - 同一用户多账号注册会被计成多个用户;
  - 跨渠道同一用户在 traffic 表里被重复计数,与 orders 表对不上。
- **当前数据能否算**:**能**。`orders.用户ID` 可直接去重;
  `traffic.支付人数` 是渠道级去重,与订单口径不同,报告必须声明。

### 候选 C:复购用户贡献的 GMV 占比

- **定义公式**:`SUM(orders.支付金额 WHERE 用户在窗口内有 ≥2 笔干净支付订单) / gmv`,
  等价于 `老客 GMV / 总 GMV`。
- **能回答什么决策**:增长靠的是拉新还是老客复购、复购运营是否在产生实际收入、
  新客质量是「一次性」还是「有潜力转复购」。
- **被操纵的风险**:
  - 观察窗口过短(如 30 天)会让复购占比天然偏低;
  - 窗口右删失会让最后一个月入场的用户没有复购机会;
  - 同一用户 1 天多笔订单是否都算「复购」,与复购率口径一致。
- **当前数据能否算**:**能**。依赖 `repurchase_rate` 的用户划分逻辑,
  只需对「有 ≥2 笔干净支付订单的用户」重新汇总 GMV。

### open_questions:三个候选的取舍

| 维度 | 候选 A 净 GMV(质量) | 候选 B 支付用户数(规模) | 候选 C 复购 GMV 占比(留存) |
|---|---|---|---|
| 核心关注点 | 收入的「净量」是否达标 | 人群规模是否在扩大 | 老客是否在持续贡献收入 |
| 最适合谁用 | 财务 / 运营负责人(复盘) | 渠道运营(拉新) | 用户运营(留存) |
| 指标稳定性 | 高(退款金额相对稳定) | 中(大促期间波动大) | 低(观察窗敏感) |
| 被操纵的难易 | 低 | 中(刷单可抬高) | 高(窗口切法影响大) |
| 与现有指标映射 | `gmv` − `refund_rate` 派生 | `order_count` 派生 | `repurchase_rate` + `new_customer_ratio` 派生 |
| 是否已有对应 id | TODO(候选块) | TODO(候选块) | TODO(候选块) |
| **推荐场景** | 月度经营会、财务对账 | 渠道预算分配、活动复盘 | 留存专项、RFM 分层 |

> **本包立场**:默认在同一份报告中同时列出三个候选值,并在结论里明确本次分析采用哪个作为
> 主要北极星指标,理由写进「口径与数据版本」一节。不允许一个季度用 A、下个季度换成 B 却不声明。

## 2. 指标树

### 2.1 三条分解链(恒等式)

每条链的叶子节点必须在 `metrics.yaml` 里有对应 id,没有的标 TODO。

**链一:GMV 拆解(规模 = 用户数 × 客单)**

```
gmv
 ├── payment_user_count TODO(候选 B,当前无独立 id)
 └── aov(= gmv / order_count, draft)
      ├── gmv
      └── order_count(confirmed)
```

> 注意:GMV 既出现在顶层又出现在 aov 的分母上,因为 aov 的公式本身就是 gmv / order_count。
> 这不是循环依赖,而是自包含恒等式;报告里可以按任意层截断,但必须声明是「规模拆解」还是「客单拆解」。

**链二:支付用户数拆解(用户数 = 流量 × 转化)**

```
payment_user_count TODO
 ├── 访问人数(来自 traffic 表,不是 orders 表)
 └── pay_conversion_rate(= 支付人数 / 访问人数, draft)
      └── cart_add_rate(= 加购人数 / 访问人数, draft) ← 漏斗中间节点
```

> 这条链的关键假设:`traffic.访问人数` 与 `orders` 的实际访问人群是同一组人,
> 但当前数据里 traffic 是渠道级聚合表、orders 是订单样本,两者**不能直接对账**,
> 详见 §3。

**链三:GMV 增量拆解(增量 = 新客 + 老客复购)**

```
Δgmv
 ├── new_customer_ratio(draft) × gmv     ← 新客贡献
 └── repurchase_rate(draft) × gmv        ← 老客复购贡献
      └── repurchase_interval(draft)     ← 复购速度
```

> 这条链用的是近似乘法:`新客 GMV ≈ 新客占比 × 总 GMV`,严格来说应该用
> `SUM(支付金额 WHERE 新客 = 是)`,但乘法近似足够用于趋势分析,报告中需注明。

### 2.2 问题 → 分解链 → 必报指标

| spec.md 问题 | 走哪条分解链 | 必报指标(id) | 核心观察 |
|---|---|---|---|
| **Q1** 增长到底来自哪里? | 链一(规模) + 链三(增量) | `gmv`、`order_count`、`aov`、`new_customer_ratio`、`repurchase_rate` | 规模是否涨;是新客在涨还是老客复购在涨;客单是否同步 |
| **Q2** 哪些渠道和品类该加码/收缩? | 链二(用户数) + 链一(品类维度) | `pay_conversion_rate`、`cart_add_rate`、`refund_rate`、`aov`、`attach_rate` | 渠道转化效率;品类结构;提价空间(价格带套路) |
| **Q3** 复购与用户价值该如何分层运营? | 链三(增量) + `repurchase_interval` 横向 | `repurchase_rate`、`repurchase_interval`、`new_customer_ratio`、`gmv` | 复购率水平;复购间隔速度;cohort 留存衰减 |

## 3. 统一漏斗与用户路径

把六个用户行为段串成一条统一漏斗,同时覆盖 `traffic.csv` 的聚合数据与 `orders.csv` 的订单数据。

| 漏斗段 | 分子列 | 分母列 | 数据来源表 | 可算性 | 备注 |
|---|---|---|---|---|---|
| **① 曝光** | `traffic.曝光人数` | —(漏斗起点) | `traffic` | 可算 | 线下门店无曝光明细,只能给线上三渠道 |
| **② 访问** | `traffic.访问人数` | `traffic.曝光人数` | `traffic` | 可算 | 线下门店有访问人数(到店人数,口径与线上不同) |
| **③ 加购** | `traffic.加购人数` | `traffic.访问人数` | `traffic` | 可算(仅线上) | 线下门店无加购明细,跨渠道漏斗只能从「访问」开始比 |
| **④ 下单** | `traffic.下单人数` | `traffic.加购人数` | `traffic` | 可算(仅线上) | 线下门店无下单漏斗中间段 |
| **⑤ 支付** | `traffic.支付人数` | `traffic.访问人数`(或下单人数) | `traffic` | 可算 | `pay_conversion_rate` 的分母由 open_questions 决定 |
| **⑥ 复购** | 窗口内有 ≥2 笔干净支付订单的用户 | 窗口内有 ≥1 笔干净支付订单的用户 | `orders` + `users` | 可算 | 不在 traffic 表,需要订单表重算 |

**必须明确写在报告里的两件事**:

1. **线下门店没有曝光与加购明细**,跨渠道漏斗**只能从「访问」段开始比较**。把线下门店的「访问人数」直接和线上三渠道摆在一起时,报告必须注明两者的「访问」定义不同(线下是到店人次,线上是页面去重访问)。

2. **`traffic` 表与 `orders` 表不能直接对账**。`traffic` 是渠道级聚合表(按日期×渠道×实验组),`orders` 是订单级样本;两者按日期+渠道近似对齐,但**同一日期同一渠道的 `traffic.支付人数` 与 `orders` 的干净支付用户数通常不一致**,原因包括:`traffic` 按用户去重、`orders` 按订单样本、跨渠道同一用户被重复计数、刷单被排除等。报告中不能声称两者一致。

## 4. AARRR 映射(只做覆盖检查)

AARRR 只用于**快速检查指标覆盖是否有盲区**,不作为分析步骤。**不要把它写进报告正文**。

| AARRR 阶段 | 对应漏斗段 | 可用指标 id | 数据是否支持 | 缺口 |
|---|---|---|---|---|
| **Acquisition(拉新)** | ② 访问 → ③ 加购 | `cart_add_rate`、`pay_conversion_rate` | 部分支持 | 访问人数是聚合的,没有渠道级新客访问与老客访问拆分 |
| **Activation(激活)** | ③ 加购 → ④ 下单 | `pay_conversion_rate`(漏斗中间可派生) | 部分支持 | 只有下单人数与支付人数两段,缺少「首次下单」标记 |
| **Retention(留存)** | ⑤ 支付 → ⑥ 复购 | `repurchase_rate`、`repurchase_interval`、`new_customer_ratio` | 支持 | 观察窗 90 天,最后一个月入场的用户有右删失 |
| **Revenue(收入)** | 整个漏斗 | `gmv`、`order_count`、`aov`、`attach_rate`、`refund_rate` | 支持 | 毛 GMV vs 净 GMV 口径待确认(open_questions) |
| **Referral(推荐)** | — | — | 无数据,不分析 | 当前五张表都没有邀请/分享字段,需要后续补数据源 |

## 5. 5W2H 澄清清单(给缺信息时用)

当用户问题模糊到无法直接生成指标时,用这 7 个问题逐步收敛。每个问题给一句示例追问,
Agent 在 `planner` 节点可以**一次性抛出多个问题**让用户确认,也可以**逐个追问**。

| 问题 | 含义 | 示例追问 |
|---|---|---|
| **What** | 分析哪个指标 / 现象? | 「你要看 GMV、订单数还是客单价?要看销量趋势还是退款率拆渠道?」 |
| **Which** | 哪张表 / 数据集? | 「用 orders.csv 还是 traffic.csv?需要关联 products 看品类吗?」 |
| **When** | 时间窗与对比基准? | 「看 2026 年 1 月还是整个 Q1?和去年同期比还是和上月比?」 |
| **Where** | 渠道 / 地区 / 品类维度? | 「按渠道拆(线下/线上/小程序/直播),还是只看直播频道?看哪些地区?」 |
| **Who** | 人群:新客 / 老客 / 会员等级? | 「新客和老客分开看吗?需要按会员等级分层吗?」 |
| **How** | 口径:毛 / 净、订单 / 用户? | 「GMV 用毛口径还是净口径(扣退款)?客单价按订单算还是按用户算?」 |
| **How much** | 阈值:多少算显著 / 算异常? | 「退款率超过多少算警戒线?AB 实验 p 值多小算显著?客单价差多少算重要?」 |

### 模糊问题 → 澄清后问题(2 个例子)

| 模糊问题 | 澄清过程(被追问的 5W2H) | 澄清后问题 |
|---|---|---|
| **「分析一下销售」** | Which → orders.csv; When → 2026-01-01~03-31, 对比上一季度; Where → 按渠道拆分; How → 支付口径毛 GMV; What → GMV 趋势 + 渠道贡献 | 「分析 orders.csv 2026-01-01~03-31 的 GMV,按渠道拆分,用支付口径毛 GMV,对比上一季度」 |
| **「看看直播效果怎么样」** | Which → traffic.csv + orders.csv 关联; When → 2026 年 2 月(直播大促集中在情人节); Where → 直播渠道 vs 线上商城; How → 支付转化率 + 客单价; How much → 统计显著 p < 0.05 | 「对比 traffic.csv 中直播渠道与线上商城 2026-02 的支付转化率和客单价差异,AB 检验显著性阈值 p < 0.05,并同时在 orders.csv 里交叉验证客单价」 |

## 6. 与现有文档的关系

- 本文件**不替代** `metrics.yaml`(指标定义)、`schema.md`(字段契约)、`playbooks.md`(步骤套路);
- 本文件只回答「先看什么、怎么拆、缺信息时问什么」;
- 所有北极星候选、漏斗段、AARRR 映射的叶子节点,最终都要回到 `metrics.yaml` 的 id;
- 新增独立指标时,先在 `metrics.yaml` 登记(状态 draft),再回来更新本文件中的分解链与 open_questions。
